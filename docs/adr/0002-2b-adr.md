# ADR-0002: Use an asynchronous post-order workflow with RabbitMQ

- **Status:** Approved
- **Date:** 2026-10-28
- **Deciders:** ชญานนท์ ทาธิจันทร์ 6870040521 (Software Architect)

## Context and problem

ตามข้อกำหนด R-12 หลังจาก Online Boutique รับคำสั่งซื้อแล้ว ระบบจะต้องดำเนินงานหลังสั่งซื้อ 3 ประการ:
1. ส่งอีเมลยืนยันคำสั่งซื้อผ่าน MailFast (ผู้ให้บริการภายนอกรายใหม่แทน mock `emailservice` เดิม)
2. มอบ loyalty points ผ่าน `loyaltyservice` ที่ต้องสร้างขึ้นใหม่
3. บันทึกเหตุการณ์ analytics ชื่อ "order placed" ให้ทีมการตลาด

จากการวิเคราะห์โค้ดเดิมใน `checkoutservice.PlaceOrder` (`system/online-boutique/src/checkoutservice/main.go`) พบว่าระบบเดิมทำงานแบบ Synchronous ใน Critical Path หากนำบริการใหม่มาต่อตรง Latency ของ MailFast (p95 1.5s, p99 8s, failure rate 0.5%, Rate limit 50 emails/s) จะส่งผลให้ `PlaceOrder` มี Latency เกินข้อกำหนด p95 ≤ 500 ms และกระทบต่อ Availability ช่วง Peak Load (200 orders/s)

นอกจากนี้ loyalty points มีข้อกำหนดทางธุรกิจว่าต้องมอบสำเร็จภายใน 1 นาทีและต้องมอบเพียงครั้งเดียวเท่านั้น (Exactly-once delivery semantics) รวมถึงระบบต้องรองรับการเพิ่มงานหลังสั่งซื้อในอนาคต (เช่น SMS, Fraud scoring, Recommendations) โดยไม่แก้ไขโค้ด Checkout หลัก

## Decision drivers

1. **Performance:** รักษา Latency p95 ของ `PlaceOrder` ให้ไม่เกิน 500 ms (ปัจจุบันอยู่ที่ ~300 ms) แม้อยู่ช่วง Peak Load 200 orders/s
2. **Availability & Fault Isolation:** คำสั่งซื้อต้องสำเร็จแม้งานหลังสั่งซื้อ (MailFast, Loyalty, Analytics) จะล้มเหลวหรือช้า
3. **Correctness & Reliability:** รับประกันการมอบ loyalty points ภายใน 1 นาที และป้องกันการเกิดผลข้างเคียงซ้ำ (Idempotency)
4. **Modifiability:** รองรับการเพิ่ม Consumer ใหม่ในอนาคตโดยไม่ต้องแก้ไข `checkoutservice`
5. **Operational Fit:** เลือกเทคโนโลยี Open-source/Self-hosted ที่ทำงานบน Kubernetes ได้อย่างมีประสิทธิภาพ

## Considered options

1. **Synchronous calls in checkout:** เรียก MailFast, `loyaltyservice` และ Analytics โดยตรงตามลำดับเดิมใน `checkoutservice`
2. **Asynchronous Event-Driven via RabbitMQ:** ใช้ RabbitMQ เผยแพร่เหตุการณ์ `order.placed` แล้วให้ Consumer แต่ละตัวแยกกันประมวลผล
3. **Workflow Orchestrator Engine:** ใช้ Workflow Engine (เช่น Temporal / Camunda) ควบคุม State และลำดับการเรียกงานหลังสั่งซื้อ

### Pros and cons of the options

| Option | Pros | Cons |
|---|---|---|
| 1. Synchronous calls | โครงสร้างเข้าใจง่าย ไม่ต้องเพิ่ม Event Infrastructure | เกินเป้าหมาย Latency p95 500ms อย่างแน่นอนเนื่องจาก MailFast latency สูง; หาก downstream ล้มอาจทำให้ Checkout ล้มตาม; แก้ไขขยายงานในอนาคตยาก |
| 2. RabbitMQ Event-Driven | แยก Critical Path ออกจาก downstream ชัดเจน; ตอบสนองได้รวดเร็ว; ปรับสเกล Consumer และจัดการ Retry/Rate limit แยกกันได้ง่าย; ทำงานบน K8s ได้ดี | เพิ่มความซับซ้อนในการบริหารจัดการ Broker, Durable Queues, Dead-Letter Exchange (DLX) และต้องทำ Idempotent Consumer |
| 3. Workflow Orchestrator | มี State Management และ Monitoring Dashboard ในตัว | ความซับซ้อนสูงเกินความจำเป็น (Over-engineering) เนื่องจากงานหลังสั่งซื้อเป็นแบบ Parallel Independent tasks ไม่มีความสัมพันธ์แบบซับซ้อน |

## Decision

ตัดสินใจเลือก **Option 2: Asynchronous Event-Driven via RabbitMQ** โดยกำหนดสถาปัตยกรรมและการทำงานดังนี้:

1. **Publisher (`checkoutservice`):** 
   - หลังยืนยันคำสั่งซื้อและบันทึก DB สำเร็จ จะทำการ Publish เหตุการณ์ `order.placed` ผ่าน **Transactional Outbox Pattern** และใช้ RabbitMQ **Publisher Confirms** เพื่อการันตีว่า Message ไม่สูญหาย
   - ตอบกลับลูกค้าทันทีโดยไม่รอผลการทำงานของบริการหลังสั่งซื้อ
2. **Exchange & Queue Topology:**
   - ใช้ **Topic Exchange** ชื่อ `order.events`
   - แยก Queue อิสระ 3 คิวสำหรับแต่ละ Consumer: `order.placed.email`, `order.placed.loyalty`, `order.placed.analytics`
3. **Consumers & Controls:**
   - **`email-consumer`:** ประมวลผลส่งอีเมลผ่าน MailFast โดยติดตั้ง **Rate Limiter (50 req/s)** และ Exponential Backoff Retry (สูงสุด 5 ครั้ง) หากล้มเหลวเกินกำหนดจะย้ายเข้า Dead-Letter Exchange (DLX)
   - **`loyalty-consumer`:** บันทึกแต้มสะสมโดยใช้ **`order_id` เป็น Idempotency Key** ตรวจสอบใน Database ก่อนประมวลผล เพื่อการันตี Exactly-once processing ภายใน 1 นาที
   - **`analytics-consumer`:** ส่งข้อมูล Analytics แบบ Asynchronous หากล้มเหลวให้ Retry ตามความเหมาะสมโดยไม่กระทบส่วนอื่น

## Consequences

- **Positive:** Latency ของ `PlaceOrder` ถูกจำกัดไว้เฉพาะการทำงานหลัก (p95 ≤ 500 ms) ผ่านการแยกภาระงาน Asynchronous
- **Positive:** ความล้มเหลวของ MailFast หรือระบบวิเคราะห์ ไม่กระทบต่อการสั่งซื้อของลูกค้า (Availability สูงขึ้น)
- **Positive:** สามารถเพิ่มงานใหม่ในอนาคต (เช่น SMS, Fraud Scoring) ได้ง่ายเพียงสร้าง Consumer เพิ่มและ Bind เข้ากับ Topic Exchange (Modifiability สูงขึ้น)
- **Negative:** ต้องแบกรับภาระการบริหารจัดการ RabbitMQ Cluster (Durable Queue, Monitoring, DLX Management)
- **Risks and mitigations:** 
  - *Risk:* Message สูญหายเมื่อ Broker ขัดข้อง -> *Mitigation:* ใช้ Durable Queues, Persistent Messages และ Transactional Outbox Pattern
  - *Risk:* การมอบแต้มสะสมซ้ำจากการ Retry -> *Mitigation:* ใช้ `order_id` เป็น Unique Constraint / Idempotency Key ใน DB ฝั่ง Loyalty Service

## Validation

1. **Performance Test:** ทำ Load Test ที่ระดับ 200 orders/s บน Kubernetes ตรวจสอบ p95 Latency ของ `PlaceOrder` ว่าไม่เกิน 500 ms
2. **Fault Tolerance Simulation:** จำลองสถานการณ์ MailFast ขัดข้อง (Latency p99 8s, Failure 0.5%) ตรวจสอบว่า `checkoutservice` สามารถทำงานได้อย่างสมบูรณ์ และคิวใน RabbitMQ สามารถ Retry จนสำเร็จได้เมื่อ MailFast ฟื้นตัว
3. **Idempotency & Retry Test:** ทดสอบส่ง Message `order.placed` ซ้ำสำหรับ `order_id` เดิม ตรวจสอบว่า `loyaltyservice` มอบแต้มเพียงครั้งเดียว และดำเนินงานเสร็จสิ้นภายใน 1 นาที
4. **Queue Monitoring:** ติดตั้ง Prometheus & Grafana เพื่อติดตาม Queue Depth, Consumer Lag, Retry Count และ DLX Message Count

## Open questions (Resolved)

- **Outbox Pattern:** ใช้ Relational Transactional Outbox บันทึก Event ลง Outbox table พร้อม Order Transaction แล้วใช้ Outbox Worker อ่านไป Publish ที่ RabbitMQ
- **Idempotency Key:** ใช้ `order_id` เป็น Idempotency Key สำหรับทุก Consumer
- **Dead-Letter Handling:** หาก Retry ครบ 5 ครั้ง (Exponential Backoff) ให้ส่งเข้า Dead-Letter Queue (DLQ) เพื่อให้ทีม OPs เข้ามา Audit และ Re-queue ได้ภายหลัง
